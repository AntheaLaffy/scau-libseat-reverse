# 华南农业大学图书馆座位预约（libseat）逆向与读图实验

2026-10-11 的实测记录。目标站点：<https://libseat.scau.edu.cn/>（图书馆座位预约）。

本文件只记录**协议与实验结果**，可以公开：没有账号、没有凭据、没有可用的会话值
（示例里的 JSESSIONID 都是占位）。账号密码只存在于工作区 `mcp/libseat/.env`，
该目录整体被 `.gitignore` 排除，不入库。

做它的起因是 `docs/AGENT.md` 的「助手作为 MCP 客户端」缺一个真实例子：助手要核实
座位、开放时间这类外部事实，而不是靠猜；站点登录又卡在图形验证码上，于是顺带把
「人/模型读图到底有多准」量了一遍。

## 站点概览

| 项 | 结论 |
| --- | --- |
| 前端 | Vite 打包的 Vue SPA，逻辑都在 `/assets/index-*.js` 及其分块里 |

### 实测到的边界与拒绝（写路径）

用真账号（`20********19`）在 2026-10-11 晚实际下单/取消，拿到这些确定性结论：

| 动作 | 结果 |
| --- | --- |
| `due` 预约**已过去**的时间段 | `无法预约已过去时间，请检查预约日期！` |
| `due` 预约**次日**（当天 20:00 之前） | 失败；`smartPlan` 的 `meta.maxDate` 也只到当天 —— 放号时间 = 规则里的 `start_time: 20:00` |
| **同一批请求 20:00 之后再跑** | ✔ 全通：`smartPlan` 的 `maxDate` 变成次日、`smartDue` 成功下单，`mine --date <次日>` 立刻能看到（`duestatu:1` 未签到），`cancel` 也能撤 |
| `due` 预约 **20:00 档**（19:32 提交） | ✔ 成功，返回完整 `order`（含 `rule`），`duestatu:1`、`signin:0`、`code: M1C002-20261011193204615683` |
| `kioskCheckIn` | `非检索机环境` |
| `signout`（未到开始时间） | `该状态不能签退,请在预约开始时间后签退` |
| `tempout`（未签到） | `该订单状态不能暂离` |
| `continueOrder` + 时间字符串 | `JSON parse error: … Integer from String "2026-10-11 20:03"` → **字段是整数分钟** |
| `continueOrder` + `30` | 类型通过，业务拒绝：`该订单状态不能续座`（需已签到） |
| `cancel`（开始前） | ✔ 成功，订单转 `duestatu:4 / dueendstatu:1`（已取消） |

结论：`签到 / 暂离 / 归位 / 续座` 这四个都要求「已签到」这个前状态；
但「设备授权」**不是绑 IP** —— 换成跟手机完全相同的源 IP、相同 UA、相同会话照样被拒；
判定依据目前只知道「普通客户端一律拒绝」，没拿到白名单本身。移动端那条 `/web/user/in` 没有这道判定。
手机端走的是另有其道的 `/web/user/in`（详见文末「补」节 —— 本节下面几段的「来源 IP」推断是错的）。

### 座位二维码解出来是什么（2026-10-11 实测）

桌上的座位贴纸二维码（M3C004）解出来是：

```
https://libseat.scau.edu.cn/use?seatName=M3C004
```

**只有座位名，没有 token、没有订单号、没有签名**。带着登录会话 GET 这个地址
（试了浏览器式与 JSON 式两种 Accept）都只是返回 SPA 外壳，订单状态不变：
这套部署里 `/use` 路由并不存在（前端路由表只有 `/`、`/checkin`、`/login`、
`/public*`、`/reserveDetails`），nginx 把未知路径兜底给了 `index.html`。
所以「把二维码交出去就能自动签到」这条不成立 —— 二维码里没有任何可回放的凭据。

### 签到到底卡在哪：~~来源 IP~~ → **接口选择**（本节是错误推断，留档，正确答案见文末「补」）

同一个订单、同一分钟，两条通路的结果：

| 来源 | IP | 结果 |
| --- | --- | --- |
| 同一位同学的手机（馆内） | `172.20.188.19` | ✔ 成功，流水中留下 `SIGN_IN 用户手机签到`，`channel: H5` |

```
2026-10-11 20:18:37  SIGN_IN    用户手机签到       channel=H5  client_ip=172.20.188.19
```

### 补：真正「手机签到」的接口是 `/web/user/in`（2026-10-11 21:25 抓包坐实）

上面那套「按来源 IP 判定」的推断后来被自己推翻了（笔记本接手机热点拿到**同一个** `172.20.188.19`，
照样被拒）。真正的答案在**接口选择**上，不在网络上：

- 订单流水的 `request_uri` 直接写了用的是哪条接口：
  `SIGN_IN … uri=/web/user/in  client_ip=172.20.188.19  用户手机签到`；
- `/api/web/user/in` **不在前端 bundle 里**（20 个 chunk 的 `url:` 全抓过，只有 `checkin/sign`），
  属于移动端/微信端那套客户端；
- 现场验证：`POST /api/web/user/in {id}` → `isOk:true`；
  同一时刻 `POST /api/web/user/checkin/sign {id}` → `。
  参数只认 `id`（`orderId`/`code`/`seatname` 都回「无法查询到该订单」），对已签到订单幂等（不新增流水）。

也就是说：`checkin/sign` 是**签到机/检索机**那条路的接口、被设备授权锁死；
`in` 是**移动客户端**的签到接口、没有设备授权判定。

## 登录链路

```
GET  /api/web/user/captcha    ->  120×40 JPEG + Set-Cookie: JSESSIONID=<占位>
POST /api/web/user/login      ->  {userName, password, captcha}    ← 必须带同一条 JSESSIONID
```

错误约定：

| 响应 | 含义 |
| --- | --- |
| `{"isOk":false,"message":"验证码错误"}` | 验证码不对（或没带上那张图对应的会话） |
| `{"isOk":false,"message":"user can not find"}` | **验证码通过了**，报错落到账号层 |
| `{"code":401,"msg":"请登录访问"}` | 会话失效，`/web/*` 的通用未登录响应 |

### 「不用 cookie」怎么落地

验证码与 JSESSIONID 强绑定，cookie 是协议的一部分，绕不过去。所以这里的做法是
**不落盘、不复用、不导出任何 cookie**：只在进程内存里维持当前会话，启动、401、
验证码失败都重走一遍 `新会话 + 新验证码 + 登录`。持久化 cookie 反而是最脆的方案——
一失效就得人工重登，还要把凭据之外的会话状态存在磁盘上。

## 验证码

实测规则：

| 规则 | 证据 |
| --- | --- |
| 与 JSESSIONID 绑定 | 不带 cookie 提交、或换一条会话提交，一律 `验证码错误` |
| 区分大小写 | 人工读得 `FYRV` 提交 → `user can not find`；`fyrv` → `验证码错误` |
| 一次一图 | 校验失败、**或那次校验通过之后**，同一张图都不再可用 → 重试必须换图 + 换会话 |
| 先验码、后查账号 | 验证码正确但账号不存在 → `user can not find` |

最后一条是这套设计的关键：**不需要一个能登录成功的账号，就能判断一个码对不对**。
`libseat_captcha_probe` 与 `readcheck.mjs` 都拿它当客观判定：
`captcha_accepted`（码被接受）/ `captcha_rejected`（码错）。

### 真账号实测：码会被消费，会话里没有「验过码」的豁免

用真账号（学号 + 密码）跑 `logintest.mjs` 得到的第二个结论，比上面更硬：

```
#2 TWCU -> 验证码通过，但登录失败：password erro        ← 码被接受，且账号确实存在
随后在**同一条会话**上，全程不抓新图：
  - 不带验证码（captcha 留空）: 验证码错误
  - 复用刚才那个已被接受的码:    验证码错误
  - 故意给个乱码（对照）:        验证码错误
```

也就是说：**验证码在「被用过一次」之后就作废**，服务端不会因为这条会话刚验过码就免检。
每次 `POST /web/user/login` 都要配一张属于当前会话的新图。

（严格地说，`登录成功后`是否仍然如此还需要一次成功登录才能盖棺定论；但既有证据都指向
「逐次校验、用完即弃」，没有会话级的豁免。`logintest.mjs` 里的 T2 就是专门测这一点的，
账号密码一通就会给出答案。）

这条结论直接决定了怎么做「固化脚本」：

| 想省掉的东西 | 办法 |
| --- | --- |
| 每次登录都要解一张图 | 求解器（自带 OCR），或者 `LIBSEAT_LOGIN_RETRIES` 多试几张 |
| 反复登录 | **别反复登录**：会话没失效就一直用（MCP 进程内已经这么做了），只在 401 时重登 |
| 依赖 agent 读图 | 上面两条都不成立时才需要；会话寿命够长的话，agent 一天也就出场一两次 |

## Agent 读图实验（本次的核心数据）

方法：抓 N 张验证码（每张各自独立会话）→ 人/模型看图读码 → **按原会话**提交
（探测账号，不涉及真实账号）→ 以服务端判定为准。

```
第 1 轮（5 张）：XHG8 ✓   YPDY ✗   PHXG ✗   SEYJ ✓   FC9C ✗    2/5
第 2 轮（5 张）：K479 ✗   ALCH ✓   ATTL ✗   9RUE ✗   49XR ✗    1/5
合计：首次命中 3/10 = 30%
```

结论：**能读，但一次读对的概率只有三成**，错例集中在连笔造成的字形歧义
（K/X、4/A、0/O、9/g）和那条横穿全图的干扰线。

这对登录流程的含义是：单图 30% 并不等于登录成功率 30%，因为**读错只损失一张图**，
不是损失一次登录机会。默认重试 5 次：

| 单图命中率 | 5 次重试 | 10 次重试 |
| --- | --- | --- |
| 30% | 83% | 97% |
| 60% | 99% | ≈100% |

所以 `login` 的语义是「失败 → 换新会话 + 新图 → 再来」，不需要人介入；读图能力本身
只决定要来回几次，不决定能不能登进去。

## 实现落点

工作区 `mcp/libseat/`（整个 `/mcp/` 已 gitignore，运行时安装，不入库）：

| 文件 | 作用 |
| --- | --- |
| `server.mjs` | stdio MCP server，36 个 `libseat_*` 工具（覆盖站点前台全部功能） |
| `seatops.mjs` | 功能操作层：找房间/挑座/拼报文/归一化返回，MCP 与脚本共用 |
| `cli.mjs` | 命令行入口，一个子命令 = 一个功能；`scripts/*.mjs` 是它的薄壳 |
| `scripts/` | 一站一功能的独立脚本 + `run-all.mjs` 全量对账 |
| `session.mjs` | 会话状态机：换图重试、401 自动重登、人工读图的两步握手 |
| `http.mjs` | 内存 cookie jar + 请求层（含 `/op/*` 的 `Idempotent-Token`） |
| `captcha.mjs` | 抓图、落盘、manifest、可插拔求解（command / http / manual / none） |
| `api.mjs` `flows.mjs` | 完整接口表（见上文）+ 探针流程（含时间窗格式归一） |
| `doctor.mjs` | 自检 CLI：配置、公共接口、抓图、真实登录、求解器探针 |
| `readcheck.mjs` | 读图能力自测：`capture N` / `submit CODE…`，输出命中率 |
| `smoke.mjs` | MCP 协议层烟雾测试（initialize / tools/list / tools/call） |
| `install.sh` | 运行时安装：装依赖、生成 `.env`、注册到 Codex、自检 |
| `solvers/ddddocr_cli.py` | 求解器接口契约的参考实现（不保证命中率） |

抓到的每张图都留三件套：**字节确定的图 + 它的 JSESSIONID + 那次登录判定**，
写成 `captcha-samples/<时间戳>-<sha256前8位>.jpg` 与 `manifest.jsonl`，
求解器可以离线回放、调参、算准确率。

安装与生效：

```bash
bash mcp/libseat/install.sh          # 装依赖 + 生成 .env + codex mcp add libseat + 自检
$EDITOR mcp/libseat/.env             # LIBSEAT_USER / LIBSEAT_PASS
node mcp/libseat/doctor.mjs --login  # 真实登录一次
```

软件内置助手侧也接同一份配置（与 `state.json` 同目录的 `mcp.json`，形状见 `docs/AGENT.md`），
工具名会变成 `mcp__seat__*` 这类；`env` 里传 `LIBSEAT_ENV_FILE` 指向 `.env` 即可。
注意助手的自动唤醒轮次不加载任何 MCP 服务器，座位这类服务器只在用户主动发起的对话里连接。

```bash
cd mcp/libseat
```

## 扩展方向：把 30% 抬上去

### 已经落地的第一步：ddddocr 基线（44%）

不用等自研模型，通用 OCR 先接上来就有明显收益：

```bash
uv run --python 3.12 --with ddddocr python solvers/ddddocr_cli.py <图片>
```

实测（假探针账号，`--probe 12`，服务端判定为准）：**9 张出码、4 张被接受，单图 44%**，
另外 3 张 ddddocr 只吐了 3 个字符（`R3u`）或吐了个汉字（`又6bc`）——它的字符集包含中文，
需要过滤。两个要点：

- **输出必须转大写**：ddddocr 的大小写不稳定（把真值 `TWCU` 读成 `TwCu`、`P9TV` 读成 `pgtv`），
  而站点校验区分大小写；已确认的正确答案全是大写字母 + 数字，所以统一 `.upper()`。
- **放大预处理没用**：3× Lanczos 之后输出仍是 `)R3u` / `又6bc`，别在这上面花时间。

44% 配 `LIBSEAT_LOGIN_RETRIES=5` 已经是 ≈95% 的登录成功率，验证码这一环不再需要人。

要再往上抬（目标单图 ≥95%），就得自己做求解器。两个方向：

1. **去干扰线预处理**：本站验证码固定带一条横穿图面的直线。按行统计黑像素比例，
   超过阈值的行整体提亮，再二值化 —— 去线后连普通 OCR 都能上一个台阶。
2. **扭曲文字 OCR**：字形是连笔手写体，通用 OCR 不友好，适合用这套
   `capture` 出来的样本训一个小模型（切分 + CNN，或直接 CTC）。

评测已经准备好了，不需要再搭一套：`doctor.mjs --probe N` 与 `readcheck.mjs`
都是拿服务端判定当标签，`manifest.jsonl` 里也留了 `jsessionid_sha256` 指纹与判定结果，
可以直接算回归基线。接入方式就是满足 `command`（`{file}` 占位、stdout 出 4 位码）
或 `http` 契约，其余代码不用动。

## 真账号登录实测（2026-10-11）

两套凭据是分开的，实测结论如下：

| 登录方式 | 凭据 | 结果 |
| --- | --- | --- |
| 站点自带的账号密码（`/api/web/user/login`） | 门户密码、旧系统两个候选 | 全部 `password erro`（账号存在，密码不对）——**用户的密码不属于这套本地账号** |
| 统一身份认证（CAS） | 门户密码 | **登录成功**，418ms，拿到 ticket 与业务会话 |

所以「密码不对」不是密码错了，而是**走错了入口**：人工登录时用的是页面上那个
「统一身份认证登录」按钮，它跟站点自带的用户名密码是两套凭据。为避免账号被锁，
本地那套在失败 4 次后就停手了。

## 统一身份认证（CAS）链路：完全免验证码

这是最终采用的登录方式（`LIBSEAT_LOGIN_MODE=cas`，默认）。协议来自
`cas.scau.edu.cn/lyuapServer` 的 SPA（`app.<hash>.js`），实测三步：

```
1. POST {CAS}/v1/tickets        form-urlencoded: username / password / service
   -> {"tgt":"TGT-182318-…","ticket":"ST-182318-…"}
2. GET  https://libseat.scau.edu.cn/sso/scau?ticket=ST-…
   -> 302 到 /?casLogin=1，并下发 webuser cookie
3. POST /api/web/pc/user        -> {"isOk":true,"data":{"user":{…}}}   # 会话已建立
```

三个关键细节（都是踩过的坑）：

- **密码不是 PKCS#1**。前端用的是「BigInt + Barrett 分块裸 RSA」：`chunkSize = 2 × 模数最高非零 16 位字`
  （1024 位模数 → 126 字节），明文按 `charCodeAt` 逐字节**小端**打包成 16 位字，
  `powMod(block, e)` 后每个 16 位字输出固定 4 位 hex、高位零字省略、分块之间空格分隔。
  用标准 PKCS#1 v1.5 会被判 `PASSERROR`（服务端解密“成功”但明文是垃圾），换成分块裸 RSA 立刻拿到 ticket。
- **公钥硬编码在前端** `app.<hash>.js` 的 module 7（`public_exponent:"010001"` + `modulus:"00b5ee…"`），
  没有单独的取公钥接口；学校换密钥时按同一位置重新提取。
- **`webuser` 是 JWT，有效期 7 天**：
  `{"iss":"zwyy-system","iat":…,"exp":…,"userId":…,"username":"…","userType":"webuser"}`，
  `exp - iat = 604800` 秒。这就是「不用反复登录」的底气。

### 顺带把最初那个问题回答清楚了

> 登录成功以后，下一次登录还需不需要图形验证码？

在**已登录的会话**上用站点自带的登录接口再登一次（不带验证码）：

```
T2 已登录会话 + 不带验证码再登录 -> 验证码错误 → 仍然需要验证码
```

也就是本地登录这条路上，**验证码是每次都要的**，跟会话说不上话（会话里没有「验过码」的豁免）。
但这个问题已经不重要了：CAS 那条路**从头到尾没有验证码**，而且会话能活 7 天。

结论——「固化成脚本、不用 agent 参与」是成立的，而且比预想的更简单：

| 方案 | 验证码 | agent 出场 |
| --- | --- | --- |
| CAS + 会话复用（**采用**） | 无 | 不需要（脚本自己在 401 时重登） |
| 本地登录 + 会话复用 | 每次登录一张 | 不需要（ddddocr 44%，5 次重试 ≈95%） |
| 本地登录 + agent 读图 | 每次登录一张 | 每次都得出场（约 10% 命中，最差） |

## 边界与未验证

- 已验证：公共接口（房间/时间片/座位）、验证码下发与全部规则、登录链路**一直到账号查询**
  （人工读对码 → `user can not find`）、401 约定、MCP 协议层（16 工具 + 真实取数）。
- 未验证：`due` 提交、`duelist`/`duedetail`、`cancel`/`checkin`/`signout`/`tempout`
  的**成功**分支——它们需要真实账号；字段与路径来自前端 bundle，站点改版时用
  `libseat_api` 逃生舱对一下即可。
- 站方规则（每人每天最多 3 次、开馆时段、开始后 15 分钟内签到、离馆 40 分钟内归位）
  仍然由服务端强制；自动化预约可能与用户协议冲突，先确认学校是否允许，别拿去做高频轮询或帮别人刷座。
