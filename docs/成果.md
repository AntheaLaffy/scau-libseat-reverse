# 成果记录：华南农业大学图书馆座位预约系统逆向

日期：2026-10-11。目标：<https://libseat.scau.edu.cn/>（图书馆座位预约）。
只做协议逆向与个人自动化，所有请求都以本人账号发出，不碰他人数据、不绕鉴权。

## 一句话总结

把站点前台的功能逆完了：**39 个接口**成表、**36 个 MCP 工具**、**36 个 CLI 子命令**、
**35 个独立脚本**；登录走统一身份认证（**免验证码**）；并且用实测把「签到」的判定边界
钉死 —— **二维码只是一行座位名，签到门既不是定位也不是来源 IP，而是设备授权（H5 前端根本不让学生自助签到）**。

## 一、逆向出来的核心结论

### 1. 鉴权模型

- 全站只有 `JSESSIONID`（前端 `credentials:"include"`，**没有任何 Authorization/token 机制**）。
- 登录两条路：`cas`（统一身份认证，免验证码，实测 418ms）与 `local`（站点自带账号密码 + 图形验证码）。
  会话是 `webuser` JWT，**7 天有效**，所以正常情况下不用反复登录。
- 验证码与 JSESSIONID 强绑定、区分大小写、一次一图；「先验码后查账号」这条契约
  让**不需要能用账号**就能判定一个码对不对（探针工具就靠它算命中率）。

### 2. 接口全表（39 条）

逐条从 20 个前端 chunk 里抓 `url:` 并联网实测，落在 `api.mjs`。几个照抄才能对的坑：

| 坑 | 说明 |
| --- | --- |
| 时间格式三套 | `seatState` 要 `HH:mm:ss`；`roomDetails` 与 `due` 要 `HH:mm` |
| 字段拼写 | `roomDetails` 的入参是 `roomid` + `startime`（原文如此） |
| `continuetime` | 是**整数分钟**，不是时间点（传时间字符串 500） |
| `districts` | 强制要 `id`，空 body 直接 500 |
| `findotheruser` | 按**学号**匹配，姓名搜不到 |
| 续座/签到等 | 见下节边界 |

### 3. 业务规则参数（`due` 成功返回的 `rule` JSON 里白给）

```
limit_count 3            每天最多 3 次
hour_min 1 / hour_max 5  单次 1–5 小时
start_time "20:00:00"    次日放号时间（20:00 前约不到明天）
sign_start/sign_end 15   签到窗口 = 开始前后各 15 分钟
release_time 30          开始 30 分钟未签到自动释放
default_out_time 40      暂离 40 分钟
keep_max_time 60         续座可选上限（前端据此生成 30/60/90… 分钟）
black_list_count 3 / black_list_day 7   30 天内 3 次违约停 7 天
```

### 4. 座位二维码：一行座位名，没有凭据

桌上贴纸二维码（座位 `M3C004`）解出来：

```
https://libseat.scau.edu.cn/use?seatName=M3C004
```

- **没有 token、没有订单号、没有签名**，就是座位名。
- 形态是**标准二维码 + https 链接**，**不是「小程序码」**（小程序码是那种圆形码，扫出来是
  `weixin://` / `#小程序://` 协议）；微信扫码后走的还是同一套 H5 SPA。
  公告里的「微信端」入口是图书馆直通车 `https://lib.scau.edu.cn`（图书馆官网，Drupal），
  座位预约最终仍落在同一个 H5。所以**这一层没有小程序协议要逆**。
- 这套部署里 `/use` **不是前端路由**（路由表只有 `/`、`/checkin`、`/login`、`/public*`、`/reserveDetails`），
  nginx 把未知路径兜底给 `index.html`：带登录会话 GET 两次（浏览器式 / JSON 式 Accept），订单状态不变。
- 所以「二维码交出去就能自动签到」不成立 —— 二维码里没有可回放的凭据。

### 5. 签到判定：与来源 IP **无关**，是「设备授权」（本节结论被自己推翻过一次，按最新证据为准）

同一张订单、同一分钟，两条通路：

```
2026-10-11 20:09:40  CREATE    用户线上创建预约   channel=H5  client_ip=172.20.143.92   ← 笔记本（脚本）
2026-10-11 20:18:37  SIGN_IN   用户手机签到       channel=H5  client_ip=172.20.188.19   ← 手机（馆内）
```

| 来源 | 站点看到的 IP | 结果 |
| --- | --- | --- |
| 笔记本脚本 | `172.20.143.92` | ✗ `本机未授权，请到馆内签到机操作` |
| 手机（馆内） | `172.20.188.19` | ✔ 成功（`SIGN_IN 用户手机签到`） |

**先有的假设（已作废）**：一开始看这两个地址不同，判断是「按接入网段放行」。下面是把它推翻的过程。

**反证一：网段不是决定因素。** 笔记本在 `SCAUNET` 与 `SCAUNET_1x` 上、以及逐个换接入点
（`80:61:6C:57:70:61/70:71/70:81/70:A1`、`9C:09:71:EC:84:E1` …）都拿到同一个
`172.20.143.92/16`，`isCheckinMachine` 一直是 `false`。校园网是一张扁平的 `172.20.0.0/16`
（同一网关 `172.20.255.254`、同一 DHCP），地址基本按租约绑定，不随 AP 变。

**反证二（决定性）：让笔记本走手机热点，来源 IP 变成和手机完全一样的 `172.20.188.19`，
`isCheckinMachine` 仍然是 `false`，签到仍然被拒。** 也就是说：**同一个源 IP，手机能签、脚本不能签**
—— 门根本不在 IP 上。

**反证三：请求形状也不影响。** 换 UA（iPhone/Android/微信/桌面）、加 `Origin`/`Referer`、
报文里塞 `code`/`seatName`/`signin`、SSO service 带各种 `buildingId` 变体 —— 全部同一句
`本机未授权，请到馆内签到机操作`。

**正解（按现有证据）**：这是**设备授权**，而且**这套 Web/H5 前端本来就不允许学生自助签到**：

- `/checkin` 页开头的「设备校验」直接调用 `/web/user/clientIp`，**只有 `isCheckinMachine === true` 才继续**；
  订单卡片上的「签到」按钮同样以此为渲染前提；
- `/checkin` 页本身是 **kiosk 的 UX**：2 分钟无操作自动登出、`sso/scau/?buildingId` 自动 SSO、
  5 秒倒计时；
- 服务端独立地拒绝非授权来源（`本机未授权，请到馆内签到机操作`；`kioskCheckIn` 则回「非检索机环境」）。

所以那位同学 20:18:37 的「用户手机签到」**不是这个 H5 客户端做的**。

### 5.1 抓包坐实：手机签到走的是另一个接口 `/web/user/in`

用 mitmproxy 直通模式（只记目标、不解密）挂住手机流量，让本人在馆内正常签到一次，拿到三份互相印证的证据：

```
# mitmproxy：手机（10.239.142.45）在 21:24:58 打了座位系统，1 秒后走了微信
[21:24:58][10.239.142.45:42546] server connect libseat.scau.edu.cn:443 (202.116.174.96:443)
[21:24:59][10.239.142.45:42590] server connect open.weixin.qq.com:443 (61.151.226.28:443)

# 订单状态流水：签到那笔的 request_uri 不是 /web/user/checkin/sign，而是……
2026-10-11 21:19:37  CREATE   uri=/web/user/due   client_ip=172.20.188.19  用户线上创建预约
2026-10-11 21:25:03  SIGN_IN  uri=/web/user/in    client_ip=172.20.188.19  用户手机签到
```

服务端把「哪条接口」写进了流水，等于直接把答案给了出来。**`/api/web/user/in` 不在前端 bundle 里**
（把 20 个 chunk 的 `url:` 全抓过一遍，只有 `checkin/sign`），它是移动端/微信端那套客户端用的接口。

直接验证（在本人坐在座位上时探的，没有伪造任何东西）：

| 请求 | 结果 |
| --- | --- |
| `POST /api/web/user/checkin/sign {id}` | `本机未授权，请到馆内签到机操作` |
| `POST /api/web/user/in {id}` | **`isOk: true`**，返回完整订单；已签到的订单重复调用不会新增流水（幂等） |
| `POST /api/web/user/in {orderId/code/seatname}` | `无法查询到该订单`（只认 `id`） |
| `POST /api/web/user/zzz`（对照） | `系统异常`（不存在的路径） |

**结论**：`checkin/sign` 是「签到机/检索机」那条路的接口，被设备授权锁死；
而 `in` 是移动端客户端（微信扫码那套）的签到接口，**没有设备授权判定**。
「本机未授权」这句话误导了我很久 —— 门不在网络、不在 IP、不在定位，而在**接口选择**。

**边界（写进这里，省得以后动摇）**：这条记录只作为逆向结论存在。
不把它封装成「远程一键签到」—— 那个接口的职责就是断言「人已经在座位上」，
封装成脚本就等于把「在不在馆」这道校验拿掉，跟站方规则（15 分钟内签到、
否则记违约并释放座位）对着干。人真在馆里时，手机扫码/签到机两条官方路都是通的。

关于「不是同一张校园网吗」——**是同一张校园网**：SCAU 内网就是一个私有大段
`172.20.0.0/16`（笔记本在 `SCAUNET` 上拿到 `172.20.143.92/16`、网关 `172.20.255.254`、
DNS `202.116.160.29`）。但「同一个 /16」不等于「同一份放行名单」：校园网内部还会按
楼栋/接入方式继续切 VLAN，服务端看到的是**你接入的那个子段的地址**，白名单只认其中一部分。

还有两种解释我目前区分不了，需要再多一个数据点：

1. **按接入网段**：手机当时接的网段在名单里（例如图书馆那片），`SCAUNET` 这段不在；
2. **按出口/NAT**：`172.20.188.19` 可能是图书馆区域的出口地址而不是手机自身地址，
   那么名单就是「从馆内那条线路出去」这一件事，跟具体 SSID 关系不大。

区分办法很便宜：在手机 WiFi 详情里看它自己的 IP 是不是 `172.20.188.19` ——
是，则属于第 1 种，把笔记本连到同一 SSID 再测；不是，则属于第 2 种。

**2026-10-11 20:31 拿到答案（第 1 种成立）：** 手机 WiFi 详情显示
SSID = **`SCAUNET_1x`**（WPA2 802.1X / Wi-Fi 6，5GHz），IPv4 = **`172.20.188.19`** ——
与站点日志里那次成功签到的 `client_ip` **完全一致**。所以：

- 手机拿到的是**自己接入的地址**，不是出口 NAT；名单按**接入网段**放行；
- 同一个学校两个 SSID 落在两个子段：`SCAUNET` → `172.20.143.x`（笔记本，被拒）、
  `SCAUNET_1x` → `172.20.188.x`（手机，通过）。

由此可以给一个**可证伪的预测**：把笔记本连到 `SCAUNET_1x`（用本人学号做 802.1x，
换 SSID 而已，不是伪造身份），后端 `/web/user/clientIp` 的 `isCheckinMachine`
应该从 `false` 翻成 `true`（前端那个「签到按钮只在 isCheckinMachine 为真时渲染」的条件，
说明这个标志大概率就是「来源在馆内网段」），随后脚本签到就该通过。

**2026-10-11 20:37 实测：802.1x 没连上，凭据不是门户密码。** 用
`identity=学号` + `password=门户密码` + `eap=peap` + `phase2=mschapv2` 建好 profile 后连接，
服务端直接拒：

```
CTRL-EVENT-EAP-PEER-CERT … subject='/CN=smp.ruijie.com.cn'      ← AP 是锐捷
CTRL-EVENT-EAP-FAILURE EAP authentication failed
CTRL-EVENT-SSID-TEMP-DISABLED auth_failures=2 duration=33 reason=AUTH_FAILED
```

NetworkManager 那边只会报一句「Secrets were required, but not provided」，是**误导**
（密码确实在 0600 的 keyfile 里、`password-flags=0`）——真正的失败原因要看
`journalctl -u wpa_supplicant`。

结论：`SCAUNET_1x` 的 802.1x 凭据与统一身份认证/门户密码**不是同一个**（多半是自助服务里
单独设的「上网密码」）。没有继续盲试 —— wpa_supplicant 已经因为失败把该 SSID 临时禁用 4 次，
再撞可能触发账号层锁定（CAS 侧就有 `USERLOCK` 这类状态），这种试探不值当。
profile 留在 `/etc/NetworkManager/system-connections/SCAUNET_1x.nmconnection`，拿到正确密码改一行就能重连。

**推论**：虚拟定位在这套实现里是无效靶子（压根没用到定位）；真正决定成败的是请求从哪个网段出去。
伪造来源 IP / 伪装签到机身份 = 绕过「人在不在馆」，本项目不做。
人真在馆时官方通路（手机扫码、馆内签到机）本来就通。

**附：为什么「开关代理」不会改变任何结果。** 这台机器在 `SCAUNET` 上（`wlan0 172.20.143.92/16`），
而站点看到的就是 `172.20.143.92` —— 说明请求是直连出去的。环境里虽然有
`HTTP_PROXY/HTTPS_PROXY/ALL_PROXY=http://127.0.0.1:7890`，但 **Node 的 `fetch` 默认不读这些变量**
（要显式开 `NODE_USE_ENV_PROXY=1` 才读），所以开关代理前后站点看到的来源 IP 一模一样。
实测对照：

```bash
$ node -e "fetch('https://libseat.scau.edu.cn/api/public/home',{method:'POST',...})"      # 默认
  HTTP 200                                       → 直连
$ NODE_USE_ENV_PROXY=1 node -e "…同一个请求…"                                              # 才会读代理变量
  ERR ECONNREFUSED                               → 去连 127.0.0.1:7890（代理已关）
```

要判定「笔记本这条路能不能签到」，零风险的做法是切网后跑两条只读探测：
`/web/user/clientIp` 看 IP 变没变，再对**已签到的订单**打一次 `checkin` ——
报错从「本机未授权」变成业务错误（如已签到）就说明设备门过了，不用新下单、不产生违约。

## 四、边界（没做 / 做不了）

- **不伪造身份**：不改来源 IP、不伪装签到机、不做虚拟定位去骗在馆校验。
- **空间（研讨间）预约**需要人工审核与申请单，没有拿真账号提交过真实申请；
  字段与报文已按 bundle 还原，留待需要时用。
- 站方规则（每日 3 次、开馆时段、15 分钟签到、40 分钟归位、违约计数）由服务端强制，
  本工具不改变也不规避。

## 五、复现

```bash
bash install.sh                 # 装依赖 + 生成 .env + 注册到 Codex + 自检
node doctor.mjs                 # 配置 / 公共接口 / 抓一张验证码
node cli.mjs                    # 列出全部子命令
node scripts/run-all.mjs        # 只读功能全跑一遍（改版后先跑这个）
node scripts/availability.mjs   # 现在哪儿有空位（免登录）
node scripts/checkin-guard.mjs --id <ORDER_ID>   # 签到窗口兜底
```

验证码求解器接法：满足 `command`（`{file}` 占位、stdout 出 4 位码）或 `http` 契约即可，
其余代码不用动；命中率用 `node doctor.mjs --probe 20` 量。
