# 成果记录：华南农业大学图书馆座位预约系统逆向

日期：2026-10-11。目标：<https://libseat.scau.edu.cn/>（图书馆座位预约）。
只做协议逆向与个人自动化，所有请求都以本人账号发出，不碰他人数据、不绕鉴权。

## 一句话总结

把站点前台的功能逆完了：**45 个接口路径**成表（另有一条只属于移动端的 `/web/user/in`，只记录不接入）、
**36 个 MCP 工具**、**36 个 CLI 子命令**、**36 个脚本**（34 个功能脚本 + 全量对账 + 签到兜底）；登录走统一身份认证（**免验证码**）。两件靠实测才敢下结论的事：
**座位二维码只是一行座位名（没有 token/签名）**；以及**签到的门不在网络、不在定位、
不在设备，而在「走哪条接口」** —— 网页端 `checkin/sign` 被设备授权锁死，
手机端用的是另一个不在前端 bundle 里的 `/api/web/user/in`。

## 一、逆向出来的核心结论

### 1. 鉴权模型

- 全站只有 `JSESSIONID`（前端 `credentials:"include"`，**没有任何 Authorization/token 机制**）。
- 登录两条路：`cas`（统一身份认证，免验证码，实测 418ms）与 `local`（站点自带账号密码 + 图形验证码）。
  会话是 `webuser` JWT，**7 天有效**，所以正常情况下不用反复登录。
- 验证码与 JSESSIONID 强绑定、区分大小写、一次一图；「先验码后查账号」这条契约
  让**不需要能用账号**就能判定一个码对不对（探针工具就靠它算命中率）。

### 2. 接口全表（45 条路径 / 46 个方法）

逐条从 20 个前端 chunk 里抓 `url:` 并联网实测，落在 `api.mjs`。几个照抄才能对的坑：

| 坑 | 说明 |
| --- | --- |
| 时间格式三套 | `seatState` 要 `HH:mm:ss`；`roomDetails` 与 `due` 要 `HH:mm` |
| 字段拼写 | `roomDetails` 的入参是 `roomid` + `startime`（原文如此） |
| `continuetime` | 是**整数分钟**，不是时间点（传时间字符串 500） |
| `districts` | 强制要 `id`，空 body 直接 500 |
| `findotheruser` | 按**学号**匹配，姓名搜不到 |
| 续座/签到等 | 见下节边界 |

### 3. 业务规则参数（`due` 成功返回的 `rule` JSON 里白给）

```
limit_count 3            每天最多 3 次
hour_min 1 / hour_max 5  单次 1–5 小时
start_time "20:00:00"    次日放号时间（20:00 前约不到明天）
sign_start/sign_end 15   签到窗口 = 开始前后各 15 分钟
release_time 30          开始 30 分钟未签到自动释放
default_out_time 40      暂离 40 分钟
keep_max_time 60         续座可选上限（前端据此生成 30/60/90… 分钟）
black_list_count 3 / black_list_day 7   30 天内 3 次违约停 7 天
```

### 4. 座位二维码：一行座位名，没有凭据

桌上贴纸二维码（座位 `M3C004`）解出来：

```
https://libseat.scau.edu.cn/use?seatName=M3C004
```

- **没有 token、没有订单号、没有签名**，就是座位名。
- 形态是**标准二维码 + https 链接**，**不是「小程序码」**（小程序码是那种圆形码，扫出来是
  `weixin://` / `#小程序://` 协议）；微信扫码后走的还是同一套 H5 SPA。
  公告里的「微信端」入口是图书馆直通车 `https://lib.scau.edu.cn`（图书馆官网，Drupal），
  座位预约最终仍落在同一个 H5。所以**这一层没有小程序协议要逆**。
- 这套部署里 `/use` **不是前端路由**（路由表只有 `/`、`/checkin`、`/login`、`/public*`、`/reserveDetails`），
  nginx 把未知路径兜底给 `index.html`：带登录会话 GET 两次（浏览器式 / JSON 式 Accept），订单状态不变。
- 所以「二维码交出去就能自动签到」不成立 —— 二维码里没有可回放的凭据。

### 5. 签到：真正的门是「接口选择」，不是网络 / 定位 / 设备

**结论先说：站点有两套签到接口，网页端那套被锁死，手机端那套不设这道门。**

| 接口 | 谁在用 | 结果 |
| --- | --- | --- |
| `POST /api/web/user/checkin/sign {id}` | 网页 SPA（`/checkin` 页、签到机 UI） | ✗ `本机未授权，请到馆内签到机操作` |
| `POST /api/web/user/in {id}` | **移动端 / 微信扫码那套客户端** | ✔ `isOk: true` |

`/api/web/user/in` **不在前端 bundle 里** —— 20 个 chunk 的 `url:` 全抓过一遍，只有 `checkin/sign`。
也就是说「本机未授权」这句提示把人往「设备 / 网络 / 定位」上带，实际的门在**走哪条接口**上。

证据来源（2026-10-11 21:25，本人坐在座位上正常签到一次）：

```
# ① mitmproxy 直通模式抓到的目标（手机 10.239.142.45）
[21:24:58][10.239.142.45:42546] server connect libseat.scau.edu.cn:443 (202.116.174.96:443)
[21:24:59][10.239.142.45:42590] server connect open.weixin.qq.com:443  (61.151.226.28:443)

# ② 订单状态流水把「用了哪条接口」写在了 request_uri 里（这招比抓包还快）
2026-10-11 21:19:37  CREATE   uri=/web/user/due   client_ip=172.20.188.19  用户线上创建预约
2026-10-11 21:25:03  SIGN_IN  uri=/web/user/in    client_ip=172.20.188.19  用户手机签到
```

现场对照（没有伪造任何条件）：

| 请求 | 结果 |
| --- | --- |
| `POST /api/web/user/checkin/sign {id}` | `本机未授权，请到馆内签到机操作` |
| `POST /api/web/user/in {id}` | **`isOk: true`**，返回完整订单；对已签到订单幂等（不新增流水） |
| `POST /api/web/user/in {orderId / code / seatname}` | `无法查询到该订单`（只认 `id`） |
| `POST /api/web/user/zzz`（对照） | `系统异常`（不存在的路径） |

**边界（写死在这里，省得以后动摇）**：`in` 只作为逆向结论记录，**不封装成「远程一键签到」**。
它的职责就是断言「人已经在座位上」，封成脚本等于把「在不在馆」这道校验拆掉，
跟站方规则（开始后 15 分钟内签到，否则记违约并释放座位）对着干。
人真在馆里时，手机扫码和签到机两条官方路都通 —— 本人当晚两次签到就是证明。
另外没有测「对**未签到**的订单调 `in` 会不会真的签上」，测了就等于拿它做不在场签到。

### 5.1 排除过程：三条死路，留档免得重走

**死路一：定位。** 这套实现里没有 GPS/定位判定 —— 虚拟定位是无效靶子。

**死路二：来源 IP / 接入网段。** 一开始按「手机 `172.20.188.19` 能签、笔记本 `172.20.143.92` 不能签」
推断「按网段放行」，后来被逐条推翻：

- 笔记本在 `SCAUNET` 与 `SCAUNET_1x`、逐个换接入点（`80:61:6C:57:70:61/70:71/70:81/70:A1`、
  `9C:09:71:EC:84:E1` …）都拿到同一个 `172.20.143.92/16` —— 校园网是扁平的 `172.20.0.0/16`
  （同一网关 `172.20.255.254`、同一 DHCP），地址按租约绑定，不随 AP 变；
- **决定性反证**：把笔记本接到手机热点后，站点看到的来源 IP 变成和手机**完全一样**的
  `172.20.188.19`，`isCheckinMachine` 仍是 `false`、签到仍被拒 —— 同一个源 IP，手机能签、脚本不能签；
- 顺带确认：手机 WiFi 详情里 SSID = `SCAUNET_1x`（WPA2 802.1X）、IPv4 = `172.20.188.19`，
  与站点日志 `client_ip` 一字不差，所以那是手机自己的地址、不是出口 NAT。

**死路三：请求形状。** 换 UA（iPhone / Android / 微信 / 桌面）、加 `Origin`/`Referer`、
报文里塞 `code`/`seatName`/`signin`、SSO service 带各种 `buildingId` 变体 —— 全部同一句拒绝。

**顺带排掉的干扰项**：`/web/user/clientIp` 的 `isCheckinMachine` 一直是 `false`（它是给
kiosk UI 用的），`/checkin` 页本身是 kiosk 的 UX（2 分钟无操作自动登出、`sso/scau/?buildingId`
自动 SSO、5 秒倒计时）；以及**开关系统代理不影响结果** —— Node 的 `fetch` 默认不读
`HTTP(S)_PROXY`（要 `NODE_USE_ENV_PROXY=1`），所以站点一直看到的是直连地址，两次一模一样。

### 5.2 方法（可复用）

1. **订单状态流水会写 `request_uri`** —— 想弄清「某个动作走了哪条接口」，先看
   `/web/seatOrderStateLog/listByOrderId {orderId}`，比抓包省事得多；这次就是靠它定位到 `in`。
2. **mitmproxy 直通模式** 抓「打到哪个域名」而不破坏功能：
   ```bash
   systemd-run --user --unit=mitm-libseat --collect \
     -p Environment=PYTHONUNBUFFERED=1 \
     -p StandardOutput=append:/tmp/mitm.log -p StandardError=append:/tmp/mitm.log \
     /usr/bin/mitmdump -p 8080 --set block_global=false --set "ignore_hosts=.*" -w /tmp/mitm.flows
   ```
   手机 WiFi 代理指向笔记本在热点里的地址（`10.239.142.180:8080`）即可；因为 `ignore_hosts=.*`
   不解密，App/微信不会报证书错误，功能照常，但每条连接的目标域名 + IP 都留在日志里。
   要看请求体再撤掉 `ignore_hosts` 并在手机上装 `~/.mitmproxy/mitmproxy-ca-cert.pem`。

## 四、复现

```bash
bash install.sh                 # 装依赖 + 生成 .env + 注册到 Codex + 自检
node doctor.mjs                 # 配置 / 公共接口 / 抓一张验证码
node cli.mjs                    # 列出全部子命令
node scripts/run-all.mjs        # 只读功能全跑一遍（改版后先跑这个）
node scripts/availability.mjs   # 现在哪儿有空位（免登录）
node scripts/checkin-guard.mjs --id <ORDER_ID>   # 签到窗口兜底
```

验证码求解器接法：满足 `command`（`{file}` 占位、stdout 出 4 位码）或 `http` 契约即可，
其余代码不用动；命中率用 `node doctor.mjs --probe 20` 量。
